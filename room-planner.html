Room Planner

An Android app for seeing a rearranged room before moving a single heavy piece of furniture.

I wanted to see how a room would look after rearranging it without dragging a wardrobe across the floor to find out it blocks a door. In the app you draw the room to the centimetre and move furniture with a finger, and while a piece moves it is checked against the other furniture, the walls, a stove’s fire clearance, radiators and the swing of every door. The same plan can also be viewed in 3D, with furniture models, a camera you orbit with a finger and a walk-through mode. The demo below runs the app’s own placement code in your browser, compiled from Kotlin to JavaScript.

The plan, in 2D

First you draw the room to the centimetre: drag walls and corners, slide doors, windows and radiators along the walls. Then you place the furniture with a finger. Every piece is checked while it moves: red is a collision, orange a note, such as a clearance that has to stay free, and the bar at the bottom sums it up as “All OK” or a count of problems.

      01

      Placement rules that plug in without touching each other

      Problem

      Every piece is checked five ways: against other furniture, the walls, a stove’s clearance, door swings and radiators. Each check has its own geometry and its own exceptions, such as a desk top that may stand above a radiator. Kept in one function, the checks would grow into a tangle of conditions with UI text mixed in.

      How it works

      Each check is a class implementing a one-method PlacementRule interface, registered with Hilt as an @IntoSet multibinding. LayoutAnalyzer runs whatever set of rules it is given and sorts the results by severity. Rules return typed issues, not text: PlacementIssue is a sealed hierarchy, and the UI turns each type into a localised message in one when, so a new issue type is a compile error until it has a message.

      What it shows

      Code that is open for extension: adding a rule is one new class and one Hilt provider, with no change to the analyzer or the other rules. Each rule is tested on its own, and the demo above runs the same five.

      RadiatorRule

      class RadiatorRule : PlacementRule {

    override fun evaluate(item: Furniture, context: LayoutContext): List<PlacementIssue> {
        val footprint = context.footprintOf(item)
        val gap = context.settings.radiatorGapCm
        return context.room.mounted<Radiator>().mapNotNull { (radiator, wall) ->
            when {
                footprint.overlaps(radiator.body(wall)) ->
                    if (item.kind.mayOverhangRadiator) OverhangsRadiator(radiator.id) else BlocksRadiator(radiator.id)
                item.kind.mayOverhangRadiator -> null
                gap > 0.0 && footprint.overlaps(radiator.frontZone(wall, gap)) -> InFrontOfRadiator(radiator.id)
                else -> null
            }
        }
    }
}
      02

      Exact collisions at any angle

      Problem

      Furniture turns to any angle, and rooms have cut corners and diagonal walls. A bounding-box check would report a collision for a sofa turned 45° that has plenty of room. And a wardrobe pushed flush against a dresser must not count as overlapping it.

      How it works

      A room can be concave, like an L, but every footprint and zone the rules compare is convex by construction: a rotated rectangle, a radiator strip, a door swing drawn as a quarter disc of eleven arc points. For convex shapes the separating axis theorem is exact: project both shapes onto the normal of every edge, and if any projection leaves a gap, they don’t touch. An overlap of up to 0.5 cm counts as touching. Sticking out through a wall is measured separately, per wall, because the room itself may not be convex.

      What it shows

      Choosing the shapes so a simple, exact algorithm fits, instead of approximating. The tolerance is a named constant shared by the rules, so “flush is fine” means the same thing everywhere.

      ConvexPolygon.penetrationDepth()

      fun penetrationDepth(other: ConvexPolygon, tolerance: Double = CONTACT_TOLERANCE_CM): Double {
    var smallest = Double.POSITIVE_INFINITY
    for (axis in separatingAxes() + other.separatingAxes()) {
        val a = project(axis)
        val b = other.project(axis)
        val overlap = min(a.endInclusive, b.endInclusive) - max(a.start, b.start)
        if (overlap <= tolerance) return 0.0
        smallest = min(smallest, overlap)
    }
    return smallest
}
      03

      Domain code with no Android in it, so it also runs on this page

      Problem

      Geometry, rules and snapping are the heart of the app and the part most worth testing. Tests that need an Android device are slow, and a domain that quietly picks up Android classes can only be tested that way.

      How it works

      The app is three Gradle modules: :domain is plain Kotlin, :data stores the project with DataStore, and :app holds the Compose UI, ViewModels and Hilt. An Android import in the domain is a compile error, not a code review comment. For this page I compiled the same domain sources with Kotlin/JS. Nothing in them changed: the build adds stand-ins for three JVM-only names (Math, @JvmInline, @Volatile) and leaves out one file the demo doesn’t need, the saved-rooms library.

      What it shows

      A layering that holds up when tested from outside: the domain moved to a different platform with only a thin facade added. The domain tests run on the plain JVM in milliseconds.

      Takeaway

      The rules, the geometry and the snapping know nothing about screens or storage, which is why they could be tested on the plain JVM and moved to a browser with only a thin facade. The trade-off I’d flag: the collision check relies on every footprint being convex. Rooms already may be concave, but an L-shaped corner sofa would have to be split into convex parts before the rules could check it.
