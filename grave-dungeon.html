Grave · System 02 of 03

Procedural dungeons

A deterministic 200×200 dungeon generator: one seed produces the whole layout — rooms, corridors with loops, treasure rooms, the exit and the key — so a save only has to store that seed.

Problem

Every run needs a new layout, yet every map must be traversable and playable — key, exit, treasure rooms as dead ends — and have loops, or you can’t shake off a chase. Loading a save must rebuild the identical dungeon on any machine.

How it works

  1. A 9-stage pipelineRooms by rejection sampling, a graph from Kruskal’s MST plus loops from the shortest rejected edges, then carving, doors, roles, interiors, chokepoints.
  2. Generate and validateEvery attempt is checked for traversability; a failed one retries on its own random stream (up to 160), and the fallback is the best result, not a crash.
  3. Deterministic by designOwn PRNG (xorshift128 + FNV-1a) instead of UnityEngine.Random; one stream per stage, so changing one stage doesn’t shift the rest.
  4. Testable without a scenePlain C#, no MonoBehaviour, in its own Grave.Generation.Layout asmdef; the scene side is DungeonBuilder → DungeonPainter → DungeonPopulator.

Full technical breakdown
  1. A 9-stage pipeline (BuildOnce): room placement (rejection sampling instead of BSP — it leaves a margin of solid rock that keeps corridors readable) → connection graph (Kruskal’s MST + loops from the shortest rejected edges) → carving rooms and corridors → doorway normalisation → room roles (hub, treasure rooms, exit, key) → interior decoration → chokepoints.
  2. Generate and validate. Every attempt goes through a traversability check; on failure the next attempt gets its own random stream (up to 160 tries), and if all of them fail, the best result is returned instead of a crash.
  3. Deterministic by design. Own PRNG (xorshift128 + FNV-1a) instead of UnityEngine.Random (global state) and string.GetHashCode() (not stable between environments). A separate stream per stage (Derive("rooms")), so changing one stage doesn’t shift the rest of the map.
  4. Decoration driven by measurement. The generator computes (recursive shadowcasting) how much of a room is visible from its entrances and adds pillars and partitions in batches until visibility drops below a threshold that depends on the room’s area.
  5. Architecture. Logic in plain C# (no MonoBehaviour) in a separate asmdef, Grave.Generation.Layout — testable without loading a scene. The scene side is DungeonBuilder → DungeonPainter (Tilemap) → DungeonPopulator (through the Built event).

private static DungeonLayout BuildOnce(string seed, LayoutParams p, DeterministicRandom random)
{
    List<Room> rooms = PlaceRooms(p, random.Derive("rooms"), out int hubIndex,
        out List<int> treasurePlots);
    List<RoomLink> links = ConnectRooms(rooms, treasurePlots, hubIndex, p, random.Derive("links"));

    var layout = new DungeonLayout(seed, p.MapWidth, p.MapHeight, rooms, links);

    CarveRooms(layout, rooms);
    DetailOutlines(layout, rooms, hubIndex, p, random.Derive("outlines"));
    CorridorCarver.CarveAll(layout, rooms, links, hubIndex, p, random.Derive("corridors"));
    DoorwayNormalizer.Apply(layout, rooms, p.DoorwayWidth);

    // Roles are assigned before the interior pass because that pass reads them: the
    // start room and the hub are deliberately left legible, and it cannot know which
    // they are until the graph has been walked.
    AssignRoomRoles(layout, rooms, links, hubIndex, treasurePlots, p);

    RoomInteriorDecorator.Decorate(layout, p, random.Derive("interiors"));
    Chokepoints.Detect(layout);

    return layout;
}
Worth knowing
  • Tests of invariants, not values: e.g. SameSeedProducesIdenticalLayout, EveryWalkableCellIsReachableFromSpawn, ImpossibleSettingsDegradeInsteadOfCrashing — over many seeds (20–500 per test), because a test like “seed 7 has 16 rooms” breaks whenever the order of random draws changes.
  • An editor tool, Tools ▸ Dungeon ▸ Layout Preview: an ASCII preview and “Measure N seeds” (rooms, corridors, retries, ms) — the parameters are tuned on a statistical sample, not on one map.
  • A real bug: the navigation grid is configured only after the Built event. Before that, the furniture had no colliders yet and enemies planned routes through tables.
  • Ties in Kruskal are broken by room index, because List.Sort isn’t stable — without it an engine update could silently change the layout for the same seed.
