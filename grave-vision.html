Vision cone

One shared light mask: the floor and the enemies are both seen through it, so anything outside the cone is simply invisible — no hiding logic.

Problem

Darkness is a mechanic: you see only what’s lit and unblocked. Visibility must be cheap every frame, respect walls, follow the torch and aiming, and never pop things in at the light’s edge.

How it works

  1. A mesh from raycastsFieldOfView casts a fan of Physics2D.Raycasts; a plain class shared with the lamps builds the mesh.
  2. One mask for every lightA second camera draws all lights into one RenderTexture; with BlendOp Max overlapping lights never darken.
  3. Everything reads the same maskThe darkness and the enemy shader (alpha *= mask): an enemy half in the cone shows only its lit half.
  4. Cheap every frameDense rays only in the cone (1/° vs 0.25/° outside), bisected shadow edges, cached buffers, a scalable mask.

In numbers

  • ≈165 vs ≈360rays per frame — calculated from the player prefab’s settings, before edge refinement
  • 15 → 20 unitsview range without → with the torch
  • 4bisection steps on each shadow edge
  • 1 maskone RenderTexture read by the darkness and every masked sprite

More detail
  1. Where it runs. FieldOfView works in LateUpdate; the mesh is built by OcclusionMeshBuilder, the same class the lamps (StationaryLightSource) use.
  2. What the mask holds. The VisionMaskRenderer camera sees only the VisionMask layer and writes an ARGB32 RenderTexture, published as the global _VisionMask. Alpha is how strongly a pixel is lit; RGB is the light’s colour — amber for a lamp or torch, neutral for sight.
  3. Who reads it. DarknessOverlay and the SpriteFovMasked shader on enemies and barrels. The light’s edge stays smooth (the mask’s gradient); wall edges stay sharp.
  4. Per-frame details. The 4 bisection steps run only on occluder edges; the angle list, buffers and delegates are cached; the mask resolution goes from 0.25 to 1×.
  5. Tied to gameplay. With a torch the cone grows to 130° and 20 units and the view takes on the flame’s colour; aiming narrows it (min. 25° pistol / 35° shotgun) — precision at the cost of situational awareness.

Codethe enemy shader and the mask writer

Assets/Shaders/SpriteFovMasked.shader · lines 79–87 — enemy: alpha × vision mask

half4 Frag(Varyings IN) : SV_Target
{
    half4 col = SAMPLE_TEXTURE2D(_MainTex, sampler_MainTex, IN.uv) * IN.color;
    half visibility = SampleVisionMask(IN.screenPos);
    col.a *= lerp(1.0h, visibility, _MaskEnabled);
    return col;
}

half4 Frag(Varyings IN) : SV_Target
{
    float softness = lerp(_EdgeSoftness, _NearEdgeSoftness, saturate(IN.uv.y));
    float edgeStart = 1.0 - saturate(softness);
    half visibility = (1.0h - smoothstep(edgeStart, 1.0, saturate(IN.uv.x))) * saturate(_Intensity);
    // RGB is the light's colour weighted by how strongly it reaches this pixel, so a
    // dim rim contributes a dim colour and cannot out-max a nearer, brighter light.
    return half4(saturate(_LightTint.rgb) * visibility, visibility);
}
Worth knowing
  • Why not a stencil. The first version used a stencil (1 bit: visible / not visible). It gave hard sprite pop-in at the edge of the light and dark outlines where two lights overlapped — so the mask became continuous.
  • Invisible, not culled. An enemy outside the light is still drawn — its alpha is multiplied by the mask. It’s per-pixel masking, which is why a half-lit enemy shows only its lit half.
  • The masked material is switched on only in Awake (FovMaskedSpriteRuntime) — in the editor (Scene view, prefabs, thumbnails) sprites look normal, because the mask doesn’t exist there.
  • Every light has its own colour and intensity through MaterialPropertyBlock, but they all share one material; a flickering lamp needs no new raycasts.
