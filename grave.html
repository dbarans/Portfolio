Grave

Systems I built for a top-down 2D game in Unity 6: procedural dungeons, visibility, pathfinding and enemy AI.

Grave is a top-down 2D survival horror game in which the player sees only what their line of sight and light sources reach. It was made by a team of four as an engineering thesis project.

Key numbers

48 Automated unit tests (Unity EditMode) All 48 cover the dungeon generator, which runs without a scene; many sweep dozens to hundreds of seeds.
4,000 Search steps allowed per enemy path (A* pathfinding) A design limit, not a benchmark: past it, the search returns the best partial path instead of stalling the frame.
~30 → ~12 ms Frame time after profiling Measured in the editor, after one profiling pass: coarser ray sampling outside the view cone, A* buffer caching and a few other fixes.

01

Procedural dungeon generator: seeded, validated, tested

Problem

Every run needs a new dungeon that is always fully connected, with no unreachable rooms and no doorways leading into solid rock. It also has to be reproducible: the same seed must produce an identical dungeon on any machine, so a level can be recreated, debugged and tested from its seed alone.

How it works

The generator is a pure C# pipeline in its own assembly, with no dependency on scenes or MonoBehaviours. It places rooms and connects them with a minimum spanning tree built with Kruskal's algorithm and Union-Find, which gives the cheapest set of corridors linking every room. A few extra edges add loops. The pipeline then carves rooms and corridors, including dead-end corridor alcoves, validates the result, and retries with a derived seed if validation fails. A deterministic random generator gives each stage its own independent stream, so changing one stage doesn't reshuffle the others. Graph analysis finds articulation points (chokepoints), the cells that would split the dungeon in two if blocked, so nothing that blocks movement is placed on them.

What it shows

Applying graph algorithms to a real game problem, and an architecture built for testing. The generator needs no scene, so 48 EditMode unit tests cover it. Many of them sweep dozens to hundreds of seeds; for example, all 500 random seeds in one test must pass validation and produce unique layouts.

Source Assets/Scripts/Generation/Layout, tests: Assets/Tests/EditMode

  2. Spanning tree

    Kruskal's algorithm joins the rooms along the shortest edges (Manhattan distance) until every room can be reached.

  3. Loops and vaults

  4. Rooms, corridors, doorways

  5. Roles and interiors

    Roles are assigned by walking the room graph: the hub, the vaults, the exit (green) and the room with the exit key. Only then come pillars, partitions and rubble, because the interior pass reads the roles.

  6. Chokepoints

    The dungeon's bottlenecks (red), marked for the systems that come later.

  7. The same dungeon in the game

RoomCorridorGenerator.cs · BuildOnce()

private static DungeonLayout BuildOnce(string seed, LayoutParams p, DeterministicRandom random)
{
    List<Room> rooms = PlaceRooms(p, random.Derive("rooms"), out int hubIndex,
        out List<int> treasurePlots);
    List<RoomLink> links = ConnectRooms(rooms, treasurePlots, hubIndex, p, random.Derive("links"));

    var layout = new DungeonLayout(seed, p.MapWidth, p.MapHeight, rooms, links);

    CarveRooms(layout, rooms);
    DetailOutlines(layout, rooms, hubIndex, p, random.Derive("outlines"));
    CorridorCarver.CarveAll(layout, rooms, links, hubIndex, p, random.Derive("corridors"));
    DoorwayNormalizer.Apply(layout, rooms, p.DoorwayWidth);

    // Roles are assigned before the interior pass because that pass reads them: the
    // start room and the hub are deliberately left legible, and it cannot know which
    // they are until the graph has been walked.
    AssignRoomRoles(layout, rooms, links, hubIndex, treasurePlots, p);

    RoomInteriorDecorator.Decorate(layout, p, random.Derive("interiors"));
    Chokepoints.Detect(layout);

    return layout;
}
02

Visibility system: a light mask rendered by a second camera and custom shaders

Problem

Everything outside the player's line of sight, enemies included, has to be hidden, and light from several sources (the player's view cone, lamps) must blend smoothly. An earlier version used the stencil buffer, which stores a simple on/off flag per pixel: sprites were cut off sharply at the edge of the light, and overlapping lights couldn't mix.

How it works

The player's view cone and every lamp go through one shared mesh builder. Where two neighbouring rays disagree (one hits and one misses, or their distances jump), a binary search between them finds the exact edge, so outlines stay sharp without casting more rays. A second camera renders these meshes into a RenderTexture with max blending, so overlapping lights take the brighter value instead of adding up. The mask keeps light level in alpha and light colour in RGB, so one texture both dims and tints the scene, and sprite shaders hide whatever no light reaches.

What it shows

Working with Unity's rendering beyond ready-made components: an extra camera, render layers, a RenderTexture, blend modes and custom URP shaders, plus replacing an architecture once it hit its limits. It also shows profiling: the view cone used to cast a full circle of rays at full density just to draw a small ring of vision around the player, and sampling that ring more coarsely was part of the pass that took the frame from ~30 ms to ~12 ms (measured in the editor).

    The same 93 rays and 4 bisection steps on each of the 11 edges: the error all but disappears for 44 extra casts. Without bisection, that accuracy would take 400 rays in the cone alone.

  8. The mask

    The ray ends form a fan of triangles, built in LateUpdate once everything else has moved. A second camera draws it into a texture: alpha is the light's strength, RGB its colour. The end of the range fades out smoothly.

  9. No mask on the sprites

    Two things read the mask: the darkness overlay and the sprite shaders. Take the mask off the sprites and the darkness alone dims them only to 1/3: the enemy behind a pillar shows through, and so do the crate, the barrels and the glass.

  10. No darkness

    The other way round: without the darkness the floor is lit, and only a sliver of the enemy shows in the light, inside the fan's outline. The sprite reads the mask itself, pixel by pixel.

  11. Behind the pillars

    The game runs on. The enemy is cut exactly along the mask's edge: it shows only in the gaps.

  12. Live

    The same thing, every frame, as the player moves. Under the player: rays · edges · casts this frame, and the time to build the mesh (median of 9 frames, measured in the editor). The white dots jump because the edges are searched again every frame.

  13. The enemy

    Glass crunches underfoot. Here the enemy's senses are switched off; in the next recording it hears the step and runs to where it came from, along a route found by A*.

half4 Frag(Varyings IN) : SV_Target
{
    half4 col = SAMPLE_TEXTURE2D(_MainTex, sampler_MainTex, IN.uv) * IN.color;

    half visibility = SampleVisionMask(IN.screenPos);
    col.a *= lerp(1.0h, visibility, _MaskEnabled);

    return col;
}
03

A* pathfinding with a capped cost per search

Problem

Enemies chase the player across a generated dungeon, a 40,000-cell grid (200×200), and no single path search may stall a frame. The worst case is an unreachable target: a plain A* explores the entire map before it gives up.

How it works

The level's colliders are sampled into a flat walkability grid. When an obstacle is destroyed, only its area is resampled, but the region labels are rebuilt in full on purpose, because opening a single cell can merge two whole regions. A flood fill splits the grid into connected regions, so an unreachable target is rejected in O(1) before any search starts. The search uses a binary heap, a priority queue that returns the cheapest node in O(log n). It reuses its buffers between searches, invalidating them with a per-search version number instead of clearing them. It also caps the number of explored nodes and returns the best partial path instead of freezing the game.

What it shows

Turning a textbook algorithm into one whose worst case is capped per search and whose setup scales with the area searched rather than the map size. How many searches run in a frame is limited separately: each enemy re-paths on a timer or when its target moves, a failed search waits before it retries, and the update budget in system 4 parks distant enemies.

In the footage

  1. A step on glass

    The player shifts their weight on the glass. Freeze frame: the noise goes out over an event bus to every listener. The blind enemy hears it because it is in range, and barrels, unlike pillars, don't block sound.

  2. The grid

    The enemy doesn't see the room, only a grid: one obstacle query at the centre of each cell, ignoring triggers. Glass leaves a cell walkable; barrels block it, even though sound passes through them.

  3. A*

    A* takes the cell with the lowest f = g + h off the queue (the outlined cells, each with its f): the cost so far plus the octile distance to the goal. It expands every cell cheaper than the route, so on a detour it expands even cells behind the enemy. Under the player: cells expanded versus the budget.

  4. The route

    Taking the goal off the queue ends the search. The route is read backwards along the parent arrows, from the goal to the enemy. Had the budget run out, the enemy would get a route to the cell closest to the goal instead of standing still.

  5. No corner cutting

    A diagonal step is allowed only when both neighbouring cells are free. By the barrel one isn't, so the route takes two straight steps and the enemy doesn't pass through the corner.

  6. After the sound

    The game runs on. The player sneaks off the glass. The enemy runs round the barrels along the route (amber), recalculated a few times a second.

  7. Where the sound came from

    Hearing tells the enemy where the sound was, not where the player is. The enemy reaches the glass, looks around and goes back to its patrol. By then the player is outside the dashed circle, inside which the enemy would sense them even in silence.

04

Enemy AI: senses built from components and a distance-based update budget

Problem

A generated dungeon holds many enemies. Each one runs a state machine (patrol, chase, investigate) and a full A* search a few times a second, even though most of them are nowhere near the player. Enemy types also differ in how they sense the player, and adding a new type shouldn't mean editing a shared base class.

How it works

EnemyBase finds its components by interface and never learns which classes are behind them. It queries every attached detector, and any of them can confirm the player. Hearing is a separate channel fed by a noise event bus: a heard noise sends the enemy to check the spot but doesn't count as detection, because a noise is only a suspicion. Each enemy's AI then runs at one of three rates by distance from the player: every frame inside a ring sized to that enemy's own sensor range, on a jittered timer further out, and not at all past a park line, where it also releases its cached path. The jitter keeps groups from ticking on the same frame.

What it shows

Composition over inheritance in practice. The blind enemy type, BlindListenerEnemy, is a subclass whose only real content is [RequireComponent(typeof(SoundPlayerDetector))]: being blind just means its prefab has no VisionPlayerDetector, and it was added without changing EnemyBase. It also shows how to budget AI cost across a large level without making enemies near the player any less responsive.

In the footage

  1. A step that carries

    The player walks at a normal pace, not sneaking. The enemy heading back to its patrol hears it and turns ("?"), and A* again finds the route to where the sound was. Watch the dashed circle round the enemy.

  2. Detected

    Once the player is inside the circle, sound is no longer needed: the enemy detects the player and gives chase ("!"). The player breaks into a run.

  3. One of many

    Freeze frame, and the camera pulls back: the game dissolves into the dungeon plan from the generator footage. The enemy that has just given chase is one of many on it.

  4. Who actually updates

    Every enemy is marked by what the game does with it. Solid marker: its AI updates every frame. Outline with a pale centre: on a timer, every 0.35 s with jitter. Hollow: not at all, because it is parked. Numbers: how many enemies are in each group.

  5. Rings measured from the player

    The full-rate ring follows from the components: a blind enemy has no sight, so its ring is smaller than a sighted one's. Past the park line the AI doesn't run; the wake line lies just inside it (hysteresis).

  6. What it costs

    The counter: how many AI updates happened in the last second, next to how many there would be with every enemy updating every frame. Below, A* searches: each pays for the cells it visits (a version stamp instead of clearing the grid), not for the whole map.

  7. The escape on the map

    The game runs on. The player outruns the enemy and leaves its detection range, but the enemy still hears the running (the thin circle: how far footsteps carry), so it stays inside the full-rate ring.

  8. What it means in play

    Once the player slows to a walk, the footsteps no longer reach the enemy. Outside the ring and out of earshot, it drops to timed updates. No enemy near the player reacts any worse for it, and the whole dungeon costs a fraction of what it would without the budget.

Takeaway

The common thread is loose coupling through data. The generator knows nothing about pathfinding, vision or AI. It produces a layout that becomes colliders, which both the A* grid and the light rays read. It also produces a list of chokepoints and corridor alcoves. Enemy placement, a separate step I wrote that runs once the dungeon is built, uses that list to set ambushes in the alcoves and to post guards beside chokepoints, never on them. The AI in turn reaches pathfinding only through narrow interfaces, so the systems work together without depending on each other's code.
