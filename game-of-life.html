Overview

I built this Conway's Game of Life simulator for Android in Unity (C#, IL2CPP) and published it on Google Play, where it now has over 15,000 downloads. Under the hood is a multithreaded engine I wrote to keep large, fast-changing patterns running smoothly, even on lower-end phones.

Engine & Performance

Bit-parallel simulation kernel

The world is partitioned into 64×64 chunks stored as ulong bitmasks. Neighbor counts for 64 cells at a time are computed with bitwise full-adders, compiled with Unity Burst as a parallel job — measured 2.2–2.5× faster than the managed version on device.

Fully parallel step pipeline

The frontier lives in native containers, not a managed dictionary, so every stage of a step — neighbour gather, kernel, delta write, frontier apply — runs as a Burst IJobParallelFor. On mobile the serial gather, not the kernel, turned out to be the real bottleneck.

Active-chunk tracking

Only chunks near cells that changed last generation are recomputed — a step costs O(active region), not O(population). Stable regions cost nothing, no matter how large.

Multithreaded generation pipeline

A background calculation thread runs up to 100 generations ahead of the display, storing per-generation deltas (born / died cells) in a lock-guarded ring buffer instead of full grid snapshots.

Delta-driven incremental rendering

The Tilemap renderer applies only each generation's born and died cells, culled to the camera view — the whole living set is never copied on the hot path.

Region-queryable living set

Live cells are stored as chunked row bitmasks, so "what is on screen" costs O(visible cells) instead of walking the whole population under the grid lock. A puffer's ever-growing static trail no longer drags throughput down.

Far-zoom LOD renderer

Zoomed out, hundreds of thousands of tiles are replaced by one quad: living cells are rasterized into an Alpha8 mask texture (one byte write per cell) and drawn in a single pass.

Direct-apply at high speed

Above the animation cutoff the calc thread publishes whole changed chunks (one 512-byte copy each) straight into the live grid and the main thread only renders, so frame rate stops gating throughput. On a 275k-cell soup: 64 → 141 gen/s, lock hold 5.6 → 2.1 ms per generation.

Procedural grid shader

Grid lines are drawn in a fragment shader on a single camera-following quad: one draw call, constant cost at any zoom, with an LOD fade when zoomed out.

Object pooling

Per-chunk buffers are pooled for near-zero steady-state GC pressure — no allocation spikes or GC hitches on mobile.

HashLife “Turbo” engine

A second, experimental engine: Gosper's HashLife with an interned quadtree and a memoised successor, jumping 2k generations per frame. On a 255k-cell Universal Turing Machine it goes from ~300 to 61,440 gen/s; on a smaller Turing machine, 3.9 M gen/s. Jumps are abortable, the node budget scales with device RAM, and a collection keeps the memo instead of discarding it.

Verified, not assumed

Every engine change is checked differentially against a brute-force reference outside Unity — many-generation runs, because a stateful cache only fails after several steps. Burst compilation of all jobs is verified headless with bcl.exe, including a negative control, and every performance claim here comes from on-device measurement.

Architecture

Multithreaded generation pipeline

A background calculation thread runs up to 100 generations ahead of the display, writing each generation's born / died delta into a lock-guarded ring buffer. The Unity main thread consumes one delta per display step and applies it incrementally. Back-pressure holds the calc thread at most 100 generations ahead, so it never races away from what the player sees. Above 10 gen/s — where birth / death animations stop — the buffer is bypassed and the calc thread publishes changed chunks straight into the live grid.

Active-chunk, bit-parallel engine

Space is split into 64×64 chunks stored as ulong bitmasks. Only chunks that changed last step — plus their one-chunk halo — are recomputed, so a step costs O(active region) no matter how large the stable population is. Each chunk's neighbour counts are evaluated 64 cells at a time with bitwise full-adders. The frontier is held in native containers, so both the neighbour gather and the kernel run as Burst-compiled parallel jobs, and the born / died delta is simply the XOR of a chunk's old and new bitmask.

Bit-parallel Life rule — 64 cells per operation Assets/Scripts/BitmaskKernel.cs

The whole Game of Life rule as bitwise arithmetic. Each ulong is 64 cells of a row; the eight neighbour counts are summed with full- and half-adders into three bit-planes, and “alive next generation” is a boolean expression over those planes. Burst compiles it to branch-free native code and IJobParallelFor runs one chunk per index. 

private static void Compute(NativeArray<ulong> nbr, bool allowBirth, NativeArray<ulong> outRows)
{
    ulong birthMask = allowBirth ? ulong.MaxValue : 0UL;

    // Three-deep sliding window over the halo-assembled rows. Each row is assembled once
    // and read at r-1, r and r+1, so six locals replace the two NativeArray(66) Temp
    // allocations this used to make on every Execute (~6000 alloc/free pairs per generation
    // at ~3000 candidates), along with all the array indexing.
    //
    // Only rows 1..64 (the chunk's own) are ever written out — rows 0 and 65 would need a
    // next-gen computed too under a full 66-row loop, but that output is always discarded
    // (they serve only as *input* halo), so skipping it changes nothing observable.
    AssembleHaloRow(nbr, 0, out ulong prev0, out ulong prev1);
    AssembleHaloRow(nbr, 1, out ulong cur0, out ulong cur1);

    for (int r = 1; r <= ChunkSize; r++)
    {
        AssembleHaloRow(nbr, r + 1, out ulong nxt0, out ulong nxt1);

        NeighborWords(prev0, prev1, out ulong aboveL0, out ulong aboveR0, out ulong aboveL1, out ulong aboveR1);
        NeighborWords(nxt0, nxt1, out ulong belowL0, out ulong belowR0, out ulong belowL1, out ulong belowR1);
        NeighborWords(cur0, cur1, out ulong selfL0, out ulong selfR0, out ulong selfL1, out ulong selfR1);

        ulong b0_0 = 0, b1_0 = 0, b2_0 = 0;
        ulong b0_1 = 0, b1_1 = 0, b2_1 = 0;

        FullAdder(aboveL0, prev0, aboveR0, out ulong aS0, out ulong aC0);
        AddBits(ref b0_0, ref b1_0, ref b2_0, aS0, aC0);
        FullAdder(aboveL1, prev1, aboveR1, out ulong aS1, out ulong aC1);
        AddBits(ref b0_1, ref b1_1, ref b2_1, aS1, aC1);

        FullAdder(belowL0, nxt0, belowR0, out ulong bS0, out ulong bC0);
        AddBits(ref b0_0, ref b1_0, ref b2_0, bS0, bC0);
        FullAdder(belowL1, nxt1, belowR1, out ulong bS1, out ulong bC1);
        AddBits(ref b0_1, ref b1_1, ref b2_1, bS1, bC1);

        HalfAdder(selfL0, selfR0, out ulong sS0, out ulong sC0);
        AddBits(ref b0_0, ref b1_0, ref b2_0, sS0, sC0);
        HalfAdder(selfL1, selfR1, out ulong sS1, out ulong sC1);
        AddBits(ref b0_1, ref b1_1, ref b2_1, sS1, sC1);

        ulong eq2_0 = (~b0_0) & b1_0 & (~b2_0);
        ulong eq3_0 = b0_0 & b1_0 & (~b2_0);
        ulong isAlive0 = cur0;
        ulong next0 = (isAlive0 & (eq2_0 | eq3_0)) | (~isAlive0 & birthMask & eq3_0);

        ulong eq2_1 = (~b0_1) & b1_1 & (~b2_1);
        ulong eq3_1 = b0_1 & b1_1 & (~b2_1);
        ulong isAlive1 = cur1;
        ulong next1 = (isAlive1 & (eq2_1 | eq3_1)) | (~isAlive1 & birthMask & eq3_1);

        // Extract inner chunk row: inner col localX == region col localX+1, so cols
        // 1..63 come from word0 shifted left by 1, col 64 from word1's MSB.
        ulong rowBits = (next0 << 1) | ((next1 >> 63) & 1UL);
        outRows[r - 1] = rowBits;

        prev0 = cur0; prev1 = cur1;
        cur0 = nxt0; cur1 = nxt1;
    }
}

// Bit0 (MSB, 1UL<<63) is the leftmost column of the word. Returns this row's left- and
// right-shifted neighbour words for both words (i=0, i=1) of a 2-word-wide row.
private static void NeighborWords(ulong w0, ulong w1, out ulong l0, out ulong r0, out ulong l1, out ulong r1)
{
    l0 = w0 >> 1;
    r0 = (w0 << 1) | (w1 >> 63);
    l1 = (w1 >> 1) | ((w0 & 1UL) << 63);
    r1 = w1 << 1;
}

private static void FullAdder(ulong a, ulong b, ulong c, out ulong sum, out ulong carry)
{
    sum = a ^ b ^ c;
    carry = (a & b) | (a & c) | (b & c);
}

private static void HalfAdder(ulong a, ulong b, out ulong sum, out ulong carry)
{
    sum = a ^ b;
    carry = a & b;
}

// Ripple-carry add into 3 bit-planes (LSB first); final carry-out dropped (safe — a
// neighbour count of 8 truncates to 0 in 3 bits, which doesn't alias counts 2 or 3).
private static void AddBits(ref ulong b0, ref ulong b1, ref ulong b2, ulong addend0, ulong addend1)
{
    FullAdder(b0, addend0, 0, out ulong s0, out ulong c0);
    FullAdder(b1, addend1, c0, out ulong s1, out ulong c1);
    FullAdder(b2, 0, c1, out ulong s2, out _);
    b0 = s0;
    b1 = s1;
    b2 = s2;
}

[BurstCompile]
public struct ComputeChunksJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<ulong> AllNbr;
    public bool AllowBirth;
    [NativeDisableParallelForRestriction] public NativeArray<ulong> AllOutRows;

    public void Execute(int index)
    {
        NativeArray<ulong> nbr = AllNbr.GetSubArray(index * HaloWords, HaloWords);
        NativeArray<ulong> outRows = AllOutRows.GetSubArray(index * ChunkSize, ChunkSize);
        Compute(nbr, AllowBirth, outRows);
    }
}
One step: only active chunks, as a chain of Burst jobs Assets/Scripts/BitmaskGenerationSolver.cs

Candidates are derived from the chunks that changed last step plus one ring around them, so the cost tracks the active region, never the population. Gather, kernel and delta counting are chained through JobHandle dependencies, and the batch size is sized to the worker count instead of a fixed constant. 

// Candidate chunks: only a chunk within 1 ring of a chunk that changed last step can
// change now (neighbourhood adjacency is symmetric), so candidates = N(_lastChanged).
// This is O(active), never a walk over all occupied chunks — the key to keeping the
// step cost independent of a large stable pattern's size.
_candidates.Clear();
foreach (long key in _lastChanged)
{
    int cx = ChunkX(key), cy = ChunkY(key);
    for (int dx = -1; dx <= 1; dx++)
        for (int dy = -1; dy <= 1; dy++)
            _candidates.Add(ChunkKey(cx + dx, cy + dy));
}

_newChanged.Clear();

_candidateList.Clear();
foreach (long key in _candidates) _candidateList.Add(key);
int count = _candidateList.Count;
LastRecomputed = count; // every candidate is, by construction, recomputed

if (count > 0)
{
    EnsureCapacity(count);
    for (int idx = 0; idx < count; idx++) _candidateKeysBuffer[idx] = _candidateList[idx];

    // Every job stage is spread across Job System worker threads (see
    // BitmaskKernel.GatherJob's doc comment for why the gather/count/write stages also
    // need to be part of this, not just the kernel).
    //
    // Batch size targets ~2 batches per worker rather than a fixed small constant: with
    // e.g. 250 candidates on a 4-worker device, a fixed batchSize=8 would schedule ~31
    // batches for only 4 workers — most of the parallel win gets eaten by per-batch
    // scheduling overhead. Aiming for ~1-2 batches/worker (the usual Job System
    // heuristic) keeps overhead low while still using every worker.
    int batchSize = System.Math.Max(1, count / (JobWorkerCount * 2));

    JobHandle gatherHandle = new BitmaskKernel.GatherJob
    {
        CandidateKeys = _candidateKeysBuffer,
        ChunkIndex = _chunkIndex,
        ChunkData = _chunkData.AsArray(),
        AllNbr = _allNbrBuffer,
        OldBlockIds = _oldBlockIds
    }.Schedule(count, batchSize);

    JobHandle kernelHandle = new BitmaskKernel.ComputeChunksJob
    {
        AllNbr = _allNbrBuffer,
        AllowBirth = allowBirth,
        AllOutRows = _allOutBuffer
    }.Schedule(count, batchSize, gatherHandle);

    // Pass 1 (parallel, depends on the kernel): per-candidate born/died bit counts +
    // changed/newIsEmpty flags. Cheap (popcount, no per-bit loop) — see
    // BitmaskKernel.CountDeltaJob's doc comment.
    JobHandle countHandle = new BitmaskKernel.CountDeltaJob
    {
        AllOutRows = _allOutBuffer,
        OldBlockIds = _oldBlockIds,
        ChunkData = _chunkData.AsArray(),
        BornCounts = _bornCounts,
        DiedCounts = _diedCounts,
        Changed = _changedFlags,
        NewIsEmpty = _newEmptyFlags,
        NewPopCounts = _newPopCounts
    }.Schedule(count, batchSize, kernelHandle);
    countHandle.Complete();
    // … prefix sum, optional per-cell delta, serial block allocation

    // Finalize pass B (parallel): every block id is now assigned and distinct, so the
    // actual bulk copies are disjoint writes — safe to spread across worker threads.
    new BitmaskKernel.ApplyJob
    {
        AllOutRows = _allOutBuffer,
        BlockIds = _blockIds,
        ChunkData = _chunkData.AsArray()
    }.Schedule(count, batchSize).Complete();
}

(_lastChanged, _newChanged) = (_newChanged, _lastChanged);
HashLife successor — Gosper's algorithm, abortable Assets/Scripts/HashLife/HashLifeSuccessor.cs

The Turbo engine's core: a memoised recursion over an interned quadtree that advances the centre of a node by 2k generations. The abort check sits only on the cache-miss path, because a jump made entirely of cache hits has nothing worth abandoning. 

/// <summary>
/// Returns the level-(m.Level - 1) node that is the central square of
/// <paramref name="m"/> advanced by <c>2^min(jTop, m.Level - 2)</c> generations.
/// Requires <c>m.Level &gt;= 2</c>. Memoizes on <paramref name="m"/> keyed by
/// <paramref name="jTop"/> (see HashLifeNode.Result / ResultJTop): for a fixed jTop the
/// effective step at every level is min(jTop, level-2), which collapses regardless of
/// call path, so one cached result per (node, jTop) is complete — see HASHLIFE_PLAN.md
/// B4.2's "why this caching is sound".
/// </summary>
public HashLifeNode Successor(HashLifeNode m, int jTop)
{
    if (m.Population == 0) return store.Empty(m.Level - 1);
    if (m.Result != null && m.ResultJTop == jTop) return m.Result;

    HashLifeNode result = m.Level == 2 ? Life4x4(store, m) : SuccessorRecursive(m, jTop);

    m.Result = result;
    m.ResultJTop = jTop;
    return result;
}

private HashLifeNode SuccessorRecursive(HashLifeNode m, int jTop)
{
    // Checked here and not in Successor: the memoised fast path above returns without
    // doing any work, so a jump that is entirely cache hits has nothing to abandon. This
    // is the miss path, which is where the seconds are. One volatile read against nine
    // dictionary probes and thirteen recursive calls is noise.
    if (abort.Requested) throw new HashLifeAbortedException();

    int k = m.Level;
    HashLifeNode a = m.NW, b = m.NE, c = m.SW, d = m.SE;

    // The nine overlapping level-(k-1) subsquares of m, in row-major order — see
    // HASHLIFE_PLAN.md B3. Join's argument order is always (NW, NE, SW, SE).
    HashLifeNode s00 = a;
    HashLifeNode s01 = store.Join(a.NE, b.NW, a.SE, b.SW);
    HashLifeNode s02 = b;
    HashLifeNode s10 = store.Join(a.SW, a.SE, c.NW, c.NE);
    HashLifeNode s11 = store.Join(a.SE, b.SW, c.NE, d.NW);
    HashLifeNode s12 = store.Join(b.SW, b.SE, d.NW, d.NE);
    HashLifeNode s20 = c;
    HashLifeNode s21 = store.Join(c.NE, d.NW, c.SE, d.SW);
    HashLifeNode s22 = d;

    int jj = jTop < k - 2 ? jTop : k - 2;

    HashLifeNode c00 = Successor(s00, jj);
    HashLifeNode c01 = Successor(s01, jj);
    HashLifeNode c02 = Successor(s02, jj);
    HashLifeNode c10 = Successor(s10, jj);
    HashLifeNode c11 = Successor(s11, jj);
    HashLifeNode c12 = Successor(s12, jj);
    HashLifeNode c20 = Successor(s20, jj);
    HashLifeNode c21 = Successor(s21, jj);
    HashLifeNode c22 = Successor(s22, jj);

    if (jj < k - 2)
    {
        // The nine partials are already advanced 2^jj (less than the max this level
        // could do) — just re-centre them, do not advance again.
        return store.Join(
            store.Center(store.Join(c00, c01, c10, c11)),
            store.Center(store.Join(c01, c02, c11, c12)),
            store.Center(store.Join(c10, c11, c20, c21)),
            store.Center(store.Join(c11, c12, c21, c22)));
    }

    // The nine partials are each advanced 2^(k-3); a second round of Successor on the
    // four re-joined quadrants adds another 2^(k-3), totalling 2^(k-2) == jj's full step
    // at this level.
    return store.Join(
        Successor(store.Join(c00, c01, c10, c11), jj),
        Successor(store.Join(c01, c02, c11, c12), jj),
        Successor(store.Join(c10, c11, c20, c21), jj),
        Successor(store.Join(c11, c12, c21, c22), jj));
}
Region query in O(visible cells) Assets/Scripts/ChunkedCellSet.cs

Answers “which living cells are on screen” without walking the population. It chooses between probing the window's chunk coordinates and walking the stored chunks, whichever is smaller — a tight window and the far-zoom LOD window sit at opposite extremes. 

/// <summary>
/// Appends the living cells inside the inclusive world bounds to <paramref name="outCells"/>
/// (not cleared first). This is the hot query: cost is O(visible cells + touched chunks),
/// never O(total population).
/// </summary>
public void CopyWindowTo(int minX, int maxX, int minY, int maxY, ICollection<Vector3Int> outCells)
{
    if (count == 0 || minX > maxX || minY > maxY) return;

    int cx0 = minX >> ChunkShift, cx1 = maxX >> ChunkShift;
    int cy0 = minY >> ChunkShift, cy1 = maxY >> ChunkShift;

    // Two ways to find the overlapping chunks: probe every chunk coordinate the window
    // spans, or walk the stored chunks and reject the ones outside it. Which is cheaper
    // flips with zoom — a tight window spans a handful of coordinates, while the far-zoom
    // LOD window can span far more coordinates than the pattern has chunks. Pick the
    // smaller of the two so neither zoom extreme degrades.
    long spanned = (long)(cx1 - cx0 + 1) * (cy1 - cy0 + 1);
    if (spanned <= chunks.Count)
    {
        for (int cy = cy0; cy <= cy1; cy++)
        {
            for (int cx = cx0; cx <= cx1; cx++)
            {
                long key = BitmaskKernel.ChunkKey(cx, cy);
                if (!chunks.TryGetValue(key, out Chunk chunk)) continue;
                EmitChunk(key, chunk, minX, maxX, minY, maxY, outCells);
            }
        }
        return;
    }

    foreach (KeyValuePair<long, Chunk> entry in chunks)
    {
        int cx = BitmaskKernel.ChunkX(entry.Key);
        int cy = BitmaskKernel.ChunkY(entry.Key);
        if (cx < cx0 || cx > cx1 || cy < cy0 || cy > cy1) continue;
        EmitChunk(entry.Key, entry.Value, minX, maxX, minY, maxY, outCells);
    }
}

Product Features

  • Infinite world — sparse storage of live cells only; pan and frame-rate-independent pinch zoom anchored between the fingers, from single cells out to patterns hundreds of thousands of cells wide.
  • Pattern Book — classic patterns (gliders, oscillators, still lifes) loaded from RLE files with a custom parser and runtime thumbnail rasterization — a tile view and a searchable list with an A–Z index rail, plus All / Large / Favourites tabs with starred favourites.
  • Save slots — a tile picker with shaded previews and camera state. Slots live in RLE files encoded on a worker thread instead of PlayerPrefs, where reading one large save alone took 4.4 s on a Pixel 6 Pro.
  • Interactive tutorial — teaches the rules by having the player draw and evolve patterns.
  • Haptic feedback — native Android vibration bridge with amplitude control.
  • Polished UI — animated with DOTween, adjustable simulation speed up to an uncapped INF mode.
  • Lab build mode (in development) — selection, clipboard with OR / XOR / OVER paste, rotate and mirror, undo budgeted in cells rather than steps, a stamp library with RLE import / export, and a TEST button that detects still lifes and oscillator periods.
