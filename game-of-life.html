Game of Life

An Android cellular-automaton simulator whose optimised engine lets a phone run patterns of hundreds of thousands of live cells.

Conway's Game of Life on an unbounded board: the player draws cells with a finger and watches them evolve. The engineering is in keeping a phone up to speed when hundreds of thousands of cells are alive.

The Game of Life in 30 seconds

A grid of cells, each alive or dead. At every step, called a generation, all cells change at once, each looking only at its eight neighbours:

  • →Birth: a dead cell with exactly 3 live neighbours comes alive.
  • →Survival: a live cell with 2 or 3 live neighbours stays alive.
  • →Death: every other live cell dies, of loneliness (0–1 neighbours) or overcrowding (4 or more).

These three rules give rise to shapes that travel across the board, guns that fire them, and patterns so large they compute, like the Turing machine in the video.

01

An engine that only computes what changes

Problem

A straightforward simulation processes every live cell in every generation, so its cost grows with the whole pattern. On a phone, large patterns slow to a crawl even when most of the board isn't changing.

How it works

The board is split into 64×64 chunks stored as bitmasks. Each step recomputes only the chunks that changed in the previous step and their neighbours, counting the live neighbours of 64 cells at once with bitwise arithmetic. The whole pipeline, not just the core computation, runs as Burst jobs on native memory: on a dense random pattern, four worker threads give 1.96× the generations per second of one (measured on a phone).

What it shows

Profiling on the target device: parallelising only the core computation gave a clear gain in the editor but no measurable difference on the phone, because the real bottleneck was the serial data gathering around it. And allocation discipline on the hot path: removing two temporary NativeArrays per chunk cut about 6,000 native alloc/free pairs per generation at around 3,000 chunks, and once warmed up the solver itself allocates nothing per generation.

private void Step(bool allowBirth, List<Vector3Int> bornOut, List<Vector3Int> diedOut, bool emitCellDelta)
{
    // …
    // Candidate chunks: only a chunk within 1 ring of a chunk that changed last step can
    // change now (neighbourhood adjacency is symmetric), so candidates = N(_lastChanged).
    // …
    _candidates.Clear();
    foreach (long key in _lastChanged)
    {
        int cx = ChunkX(key), cy = ChunkY(key);
        for (int dx = -1; dx <= 1; dx++)
            for (int dy = -1; dy <= 1; dy++)
                _candidates.Add(ChunkKey(cx + dx, cy + dy));
    }
    // …
    _candidateList.Clear();
    foreach (long key in _candidates) _candidateList.Add(key);
    int count = _candidateList.Count;

    if (count > 0)
    {
        // Batch size targets ~2 batches per worker rather than a fixed small constant.
        int batchSize = System.Math.Max(1, count / (JobWorkerCount * 2));
        JobHandle gatherHandle = new BitmaskKernel.GatherJob
        { CandidateKeys = _candidateKeysBuffer, /* … */ }.Schedule(count, batchSize);
        JobHandle kernelHandle = new BitmaskKernel.ComputeChunksJob
        { AllNbr = _allNbrBuffer, /* … */ }.Schedule(count, batchSize, gatherHandle);
        // …
    }

    (_lastChanged, _newChanged) = (_newChanged, _lastChanged);
}

Inside one step

  1. Freeze on one step

    The game stops at generation 399, with the chunks from the footage above still marked.

  2. Gathering the neighbourhood

    The camera closes in on one of the chunks the next step will recompute, and on the chunks around it. GatherJob copies what the kernel needs into one flat buffer: the chunk and its left and right neighbours in full, but only the adjacent row of each of the three chunks above and the three below. That is 198 64-bit words instead of the 576 of a full 3×3 block: two thirds less memory written per chunk, which saves about 9 MB a generation at 3,000 chunks.

  3. 64 cells in one go

    One row (the yellow line), shown bit by bit in the panel for 16 of its 64 columns. Three AddBits calls count the neighbours of all 64 cells at once, from shifted copies of rows r − 1, r + 1 and r. The counts sit in three words, one per bit of the count (bit-planes), so Conway's rules become two masks, "exactly 2" and "exactly 3". In the panel's last row, yellow cells are born and red ones die.

  4. The whole chunk

    The same arithmetic runs through all 64 rows of the chunk. In the game it runs for every candidate chunk in parallel, as a Burst job.

  5. The delta

    Births and deaths come from two bit operations per row, new AND NOT old and old AND NOT new, 64 cells at a time with no loop over cells: births in yellow, deaths in red. The recording tool compared the traced row with the engine's own result and refused to export if the two differed at all.

AssembleHaloRow(nbr, 0, out ulong prev0, out ulong prev1);

    ulong isAlive0 = cur0;

02

Simulation on a background thread, with two ways to deliver results

Problem

The simulation must never stall rendering or touch input. At low speed, each generation also has to reach the main thread on its own, because it drives the birth/death animations and haptics. At high speed, that per-generation hand-off became the bottleneck, and a faster engine actually made the frame rate worse.

How it works

Below the speed at which animations switch off anyway, each generation's changes (births and deaths) pass through a ring buffer, a fixed-size queue that reuses its slots, so the calculation thread can run ahead of the display. Above that speed there is nothing to animate, so the calculation thread itself copies whole changed chunks into the displayed state, and the main thread only renders.

What it shows

Safe multithreading around Unity's main-thread-only API: a producer–consumer design with explicit lock discipline. Two locks, one guarding the board state and one guarding the counters behind the zoomed-out density view (system 3), are always taken in the same order, which rules out deadlock. It also shows tracking down a counter-intuitive regression: switching to whole-chunk copies took a 275k-cell random pattern from 64 to 141 generations per second on a Pixel 6 Pro.

In the footage

  1. A pattern where almost every chunk changes

    Recorded in the editor, like the footage above. Paul Rendell's original Turing machine, about 36,000 cells (not the 252,000-cell universal one in the video at the top): nearly every chunk changes in every generation, about 315 of 327. Skipping unchanged chunks can't help here, so the other half of the design matters: keeping the work off the main thread.

  2. Slow: a ring buffer

    At 4 generations a second the camera closes in. Along the bottom are the ring buffer's 128 slots, one bar per generation (bar height: how many cells changed). The calculation thread fills them ahead of the display (yellow), at most 100 generations ahead; the main thread takes one at a time (the white cursor) and plays it with the birth and death animations. The slots, the cap and each generation's changes come from the game; how fast the strip fills at first is set by the recording, which steps the engine itself.

  3. Speeding up

    The speed rises to 10 generations a second, the fastest setting that still animates; above it the animations switch off anyway.

  4. Fast: whole chunks, straight across

    Above 10 the buffer is emptied and set aside, and each changed chunk is copied across in one piece: its 64 rows, 512 bytes, written by the calculation thread into the displayed state (yellow fill) while the main thread only renders. At 60 generations a second the 30 fps footage gets two generations a frame, about 630 chunk copies (315 KB). As lists of cells, the same change would be about 54,000 cells to extract from the bits and replay on the main thread.

03

Rendering cost that scales with the screen, not the pattern

Problem

Zoomed out, a pattern can put hundreds of thousands of cells on screen, and Unity's Tilemap pays a cost for every tile. Even finding which cells were visible used to mean scanning every live cell, so the game slowed down as a pattern grew, even when the growth was off-screen.

How it works

Live cells are stored in a chunked bitmask structure that answers "what's inside this camera rectangle" in time proportional to the visible area. Up close, the Tilemap receives only each generation's changes. Zoomed far out, it's replaced by one quad textured with cell density (one byte per texel) and drawn by a custom shader in a single draw call. The switch uses hysteresis, with separate thresholds for entering and leaving, so the view doesn't flicker between modes.

What it shows

Rendering optimisation in Unity (draw calls, the limits of a built-in component, level-of-detail switching) and choosing data structures by the queries they have to answer. In a benchmark outside Unity, the on-screen query stays at ~50 µs however many cells live off-screen. The old full scan had grown to 1,035 µs at 316k live cells.

04

Engine code verified outside Unity

Problem

A bug in a stateful, bit-level engine doesn't crash anything. It produces a plausible but wrong pattern, often many generations later, so watching the screen won't catch it.

How it works

A .NET console harness compiles the same solver source files that ship to the store, with a small shim stubbing Unity's collections, Jobs and Burst. Every generation of every scenario (gliders crossing chunk edges and into negative coordinates, an empty board) is compared cell for cell with a naive reference. Each run is also folded into a golden hash that a pure refactor must reproduce byte for byte. A headless Burst compile of all five jobs for ARM64 includes a negative control that must fail to compile, so a clean pass actually means something.

What it shows

Testing discipline for core game logic, beyond what the editor offers: differential testing that pinpoints the generation where a bug first appears, a golden-hash check that turns "this refactor changed nothing" into a fact, and a Burst check that is known to fail when it should, all run from the command line.

Takeaway

Measure on the target device, not in the editor: in this project the editor pointed at the wrong bottleneck.

Also in the codebase (not in the store build)

HashLife (Gosper's algorithm), a second engine that caches and reuses results in a quadtree, so repetitive patterns jump thousands of generations in one step. It has a memory budget scaled to the device's RAM and is tested against a brute-force reference.
